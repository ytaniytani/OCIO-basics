## 1. 目的

映像やCGの知識がまったくない中学生が、次の3つを「読んで納得」ではなく「さわって納得」できる状態にする。

1. **なぜ色を管理する仕組みが要るのか。** 無いと何が起きるのか、何ができなくなるのか。
2. **OpenColorIO (OCIO) が何をしている道具なのか。** 設定ファイルを自分で書き換えて、絵が変わるところまで体験する。
3. **ACES がどんな共通ルールなのか。** その中でカラーグレーディングをどこに入れるべきか、HDR にどうつながるのか。

「用語を覚えること」はゴールではない。**同じ数字が違う色になる**という事故を自分の手で起こし、それを直せるようになることがゴール。

## 3. 全体の設計方針

### 3.1 教え方の型(全章共通)

各章は次の5ステップで構成する。この順番を崩さない。

1. **こまる (Trouble)** — 実際に困っている画面を見せる。まず失敗を体験させる。
2. **なぜ (Why)** — 何が起きているのかを、比喩と図で説明する。
3. **さわる (Play)** — スライダーやトグルで自分で再現・比較する。
4. **なおす (Fix)** — 正しい設定にすると直ることを見せる。
5. **まとめ (Recap)** — 3行以内の要約と、1問のチェック。

### 3.2 中心となる比喩

サイト全体で比喩をぶらさない。以下を公式比喩として固定する。

| 概念 | 比喩 | 説明 |
|---|---|---|
| 画素の数値 | **数字だけのメモ** | 「175」とだけ書いた紙。単位がない |
| 色空間 | **単位(cm か inch か)** | 数字に意味を与える約束 |
| 色空間タグ | **メモに書いた単位のラベル** | これが無い/間違うと事故る |
| OCIO | **単位の変換表と翻訳係** | どのラベルからどのラベルへ、どう変換するかの一覧 |
| `config.ocio` | **変換表そのもの(1枚のルールブック)** | チームで同じ物を共有する |
| ACES | **世界共通の巨大な方眼紙** | みんながその上で作業すれば話が通じる |
| シーンリニア | **光の量そのもの** | 2倍の光は数値も2倍 |
| ディスプレイ参照 | **画面用に加工済みの見た目** | 数値と光の量は比例しない |
| 出力変換 (ODT / Output Transform) | **方眼紙から各テレビ用への刷り上げ** | 出力先ごとに刷り直せる |
| グレーディング | **味付け** | 刷り上げる前に入れる。刷った後にかけると出力ごとに壊れる |

### 3.3 やらないこと(スコープ外)

- OCIO の全機能網羅、API リファレンス、C++/Python バインディングの解説。
- 実在の商用ソフト(Nuke, Resolve, Maya, Unreal 等)の操作手順書。名前と役割の紹介にとどめる。
- 測色・分光の厳密な理論、CIE 標準観測者の導出。
- ICC プロファイルとの詳細比較(付録で1節だけ触れる)。
- カラリストとしての作品づくりのノウハウ。

### 4.1 各章の内容仕様

#### 第0章 このサイトの歩き方

- 3分で読める導入。「色がズレる事故」の30秒デモ動画相当(Canvas アニメーション)をトップに置く。
- 「読むだけじゃなくて、全部さわれます」と明示。
- 進捗は `localStorage` に保存。読み終えた章にチェックが付く。保存できない環境でも壊れないこと。

#### 第1章 色ってなんだろう

- 光は色の混ざりもの。目には赤・緑・青に反応する3種類のセンサーがある。
- だから色は R, G, B の3つの数字で表せる。
- **I-01 光の量スライダー**: 光源の強さを変えると、数値と見た目がどう動くか。
- ここではまだ「色空間」は出さない。数字で色が表せる、まで。
- こまる: 「175」と書いた紙を渡されても、どのくらい明るいか決まらない、を予告。

#### 第2章 数字だけでは色は決まらない

- **こまる**: 同じ `(255, 0, 0)` が、機械によって違う赤になる。写真をアプリ間でコピーしたら色がくすんだ、という日常例。
- **なぜ**: 「一番濃い赤」がどれくらい濃いかは機械ごとに違う。だから **どの赤を基準にしているか** の約束が要る。それが色空間。
- 色空間 = ①原色の位置(色域)②白の色(白色点)③数値と明るさの関係(伝達関数) の3点セット、と定義する。③は第3章に送る。
- **I-04 色度図ビューア**: sRGB / Rec.709 / Display P3 / Rec.2020 / ACES AP1 / ACES AP0 の三角形を重ねて比較。中学生向けに「使える色の広さ」と説明。
- **I-05 タグ違い事故シミュレータ**: 画像に付ける色空間ラベルをわざと間違えて、色がどう転ぶか。
- **まとめ**: 数字 + ラベル でひとセット。ラベルの無い画像は事故のもと。

#### 第3章 明るさの数字は正直じゃない

- **こまる**: 「50% グレー」は本当に光の量が半分か? → 違う。
- **なぜ**: 人の目は暗いところの差に敏感。少ないビット数を有効に使うため、画面用の数値はわざと曲げてある(ガンマ / 伝達関数)。
- 具体値を必ず出す: sRGB の数値 0.5 は、光の量にすると約 **0.214**。8bit の 128(= 数値 0.502)なら約 **21.6%**。
- 逆向きも出す: 光の量を半分(0.5)にすると、sRGB の数値は 0.735、8bit で **188**。
- 数字の目もりを必ず書く。8bit は「真っ黒 0 から真っ白 255 までの 256段階」、光の量は「真っ暗 0.0、白い紙 1.0」。中間グレー 0.18 は光の量のほう。
- **I-02 二倍の光クイズ**: 光を2倍にしたとき数値は何になる? を当てさせてから答え合わせ。
- **I-03 ガンマカーブ・エクスプローラ**: 横軸=光の量、縦軸=保存する数値。曲線上を指でなぞると対応が読める。sRGB / Rec.709 / 純ガンマ2.2 / リニア / ACEScct を切り替え。
- 用語整理: **シーンリニア**(光の量そのもの)と **ディスプレイ参照**(画面用に曲げた値)。この2語は以降ずっと使う。

#### 第4章 見える範囲がちがう

- **こまる**: 逆光で撮った写真の空が真っ白。あとから戻せない。
- **なぜ**: 保存できる明るさの幅(ダイナミックレンジ)には限りがある。8bit JPEG は白を超えた情報を捨てている。
- 目 / カメラのセンサー / スマホ画面 / HDRテレビ の守備範囲を1本の横棒グラフで比較。
- **I-06 露出スライダー + クリップ体験**: 同じシーンを「8bitで焼き付けた画像」と「シーンリニアのまま持っている画像」の2枚で用意し、露出を下げたとき何が戻るかを比べる。**この体験が第10章 HDR の伏線**になる。
- 用語: 白飛び (clipping)、階調 (gradation)、ビット深度、float。

#### 第5章 混ぜると壊れる

- **こまる**: CG の光を2倍にしたのに2倍明るく見えない。半透明の合成の境目が汚い。ぼかすと暗くなる。
- **なぜ**: 足し算・平均・ぼかしは「光の量」に対してやらないと物理的に正しくならない。曲がった数値のまま計算すると結果が狂う。
- **I-07 リニア合成ラボ**: 同じ操作(加算 / アルファ合成 / ぼかし / 縮小 / グロー)を、リニア空間と表示用空間の両方で実行して並べる。差分表示トグル付き。
- 特に効く例: 赤と緑のグラデーションを重ねたときの境界、明るい点をぼかしたときの広がり方。
- **まとめ**: 計算はリニアで。見るときだけ画面用に変換する。この「作業空間と表示空間を分ける」考え方が OCIO の土台。

#### 第6章 OCIO の登場

物語仕立て。**学園祭ムービー・プロジェクト**という設定で通す。

- 素材が4つある。
  1. スマホで撮った動画(sRGB / Rec.709 相当)
  2. 友達が一眼で撮ったログ映像(Log、眠い灰色に見える)
  3. 自分で作った 3DCG(リニア)
  4. ネットで拾ったフリー素材(ラベル不明)
- **こまる**: そのまま並べると、明るさも色もバラバラ。CG だけ暗い。ログ映像だけ灰色。編集ソフトAとBで見え方も違う。
- **I-08 事故シミュレータ**: OCIO なし / あり をトグルで切り替えて、同じタイムラインの見た目を比較。
- **なぜ**: 素材ごとに「どの色空間か」が違う。全部を一度 **共通の作業空間** に翻訳してから作業すればいい。
- OCIO の役割を1文で: **「どの色空間からどの色空間へ、どう変換するか」を1つのファイルにまとめて、全ソフトで同じ答えを出させる仕組み。**
- OCIO が無いと具体的に何ができないか、を箇条書きで明示する:
  - ソフトを移るたびに色が変わり、どれが正解かわからなくなる
  - CG と実写を合成しても馴染まない
  - SDR 用に仕上げた作品を HDR 用に作り直すには、全工程やり直しになる
  - 数年後に同じ色を再現できない
  - チームで「私の画面ではこう見える」の水掛け論になる
- **I-09 パイプライン組み立てパズル**: 入力変換 → 作業空間 → ルック → 出力変換 のブロックを正しい順に並べる。間違えると結果画像が壊れて見える。

#### 第7章 `config.ocio` をさわる

- OCIO の実体は **1つの YAML ファイル**。中身を見せる。怖くないと伝える。
- 最小構成の `config.ocio` を全文掲載し、行ごとに吹き出し注釈。
- 覚えるキーは5つだけに絞る: `roles`, `colorspaces`, `displays`, `views`, `looks`。
- **I-10 ライブエディタ**: 左に YAML エディタ、右にプレビュー画像。編集すると即座に反映。
  - 課題1: 新しい色空間 `my_gamma22` を追加して view に出す。
  - 課題2: `scene_linear` ロールをわざと間違った色空間に向けて、何が壊れるか観察する。
  - 課題3: `looks` を1つ追加して、ちょっと青くする。
  - 課題4: 出力を Rec.709 から sRGB に切り替えて差を見る。
- 実務の話も1段落だけ: 環境変数 `OCIO` に config のパスを設定すると、対応ソフトが一斉にそれを使う。公式配布の ACES 用 config(CG config / Studio config)がある。
- エラーの読み方を教える。存在しない色空間名を書くと何と言われるか、を実際に出す。

#### 第8章 ACES というみんなのルール

- ACES = Academy Color Encoding System。映画業界が作った共通ルール。
- **なぜ必要か**: OCIO は「変換のしくみ」を提供するが、**どの色空間を共通の場にするか** はチーム次第。世界中で同じ答えにするために、業界が用意した既製の答えが ACES。
- 4段階で説明する:
  1. **入力変換 (Input Transform / IDT)** — どのカメラの絵も ACES の座標に翻訳する
  2. **作業空間** — `ACES2065-1 (AP0)` は保存・受け渡し用、`ACEScg (AP1)` は CG と合成の作業用、`ACEScct` はグレーディング用
  3. **ルック (LMT / Look)** — 作品全体の味付け
  4. **出力変換 (Output Transform)** — 見る機械に合わせて刷り上げる。ACES 1.x では RRT + ODT の2段、ACES 2.0 では1つの Output Transform に統合された、と正確に書く
- **I-11 ACES 全景マップ**: 横スクロールする1枚の図。各段をタップすると、その段での画がどう見えるかのサムネイルと、1行説明が出る。
- 「なぜ作業空間が3つもあるのか」に必ず答える。用途が違うから(保存用は広く安全に、CG用は計算しやすく、グレード用は手の感触が良いように)。
- 中学生向けの落とし所: **ACES は「一度共通の方眼紙に写してから作業して、最後に出力先ごとに刷る」やり方。**

#### 第9章 カラーグレーディングはどこに入れる

この章は本サイトの山場の1つ。3つの選択肢を実験で比較する。

- グレーディングとは何か: 明るさ・色みを調整して作品の雰囲気を作る作業。フィルターとの違いは「作品全体で一貫させる」こと。
- **挿入位置の候補**
  1. **入力変換の前**(素材そのものを直接いじる)
  2. **作業空間の中**(ACEScct でグレード → その後 出力変換) ← 正解
  3. **出力変換の後**(でき上がった映像に後がけ)
- **I-12 グレーディング位置ラボ**: 同じ調整量を3か所それぞれに入れ、SDR と HDR の2つの出力で結果を並べる。
  - 位置1 の問題: 素材ごとに効き方が違う。カメラを変えると再現できない。
  - 位置3 の問題: SDR ではよくても HDR 出力に持っていくと破綻する。出力ごとにやり直しになる。白飛びが戻らない。
  - 位置2 の利点: 出力を差し替えても味付けが保たれる。ハイライトが残っている状態で調整できる。
- 実務用語の対応も入れる: **LMT** は「作品全体の共通の味付け」、**CDL / ショットグレード** は「カット単位の調整」。どちらも出力変換の **前**。
- まとめの一文: **味付けは刷る前。刷った後に足すと、刷り直すたびに壊れる。**

#### 第10章 HDR — 明るいテレビにも届ける

- **こまる**: 家のテレビは「HDR対応」と書いてある。従来の映像を映しても、その明るさを活かせない。
- **なぜ**: 従来の映像 (SDR) は「一番白いところ = だいたい 100 nit」を前提に作られている。HDR は 1000 nit 以上を扱える。
- **nit (cd/m²)** を身近な数字で示す: 室内の紙 ≒ 数十、スマホの白 ≒ 400〜1000、晴天の空 ≒ 数千以上。
- **PQ (ST 2084)** と **HLG** の違いを1行ずつ。PQ = 絶対的な明るさを指定する方式(配信・ディスク向け)。HLG = 従来テレビとも両立しやすい方式(放送向け)。
- **ここで第4章と第8章が回収される**:
  - 第4章: シーンリニアで撮って持っていたから、HDR に出す「余っている明るさ」がまだ残っている。8bit で焼いていたら何も残っていない。
  - 第8章: ACES で作業していたから、**出力変換を差し替えるだけ** で SDR 版と HDR 版が出せる。作り直しではない。
- **I-13 HDR出力比較**: 1つの ACES データから、SDR 100nit / HDR 1000nit / HDR 4000nit の出力変換を切り替え。
  - 実際に HDR 表示できる環境では本物の HDR で見せる(対応判定して切り替え)。
  - 非対応環境では「SDR画面上での擬似表現 + 明るさメーター + どこが伸びたかのヒートマップ」で見せる。**擬似表現であることを画面上に必ず明記する。**
- **1マスター多出力** の図で締める。ACES マスター1本 → 劇場 / 配信SDR / 配信HDR / SNS。

#### 第11章 まとめとチェックテスト

- 全体像を1枚の図で再掲(第8章のマップの縮小版)。

- 間違えたら該当章へのリンクを出す。点数は保存するが、順位や共有機能は作らない。

## 5. 技術仕様

### 5.1 方針

- **ビルド不要の静的サイト。** HTML + CSS + JavaScript (ES Modules) のみ。npm 依存もフレームワークも使わない。
- GitHub Pages で `main` ブランチの `/` を公開。将来 `/docs` 公開に切り替えても動くよう、相対パスのみ使う。
- 外部 CDN に依存しない。フォントも含めてリポジトリ内で完結させる。オフラインでも動くこと。
- JavaScript が無効でも、本文と図版の代替説明は読めること(インタラクティブ部品は「この機能には JavaScript が必要です」と表示)。

### 5.3 レンダリング

- 画像処理は **WebGL2** を第一手段とする。float / half-float テクスチャで作業し、色変換はフラグメントシェーダで実行。
  - 必要拡張: `EXT_color_buffer_float`(無ければ half-float にフォールバック)。
- WebGL が使えない環境では **Canvas 2D + CPU 実装** にフォールバック。解像度を落として動かす(最大 512px 長辺)。
- 1つの部品の初期表示は **モバイル実機で 300ms 以内**、操作の追従は **60fps 目標 / 30fps 下限**。
- 重い部品は `IntersectionObserver` で画面に入るまで初期化しない。

### 5.4 教材用の画像素材

権利の問題を避けるため、**実写素材は原則使わない**。

- シーンは **プロシージャル生成**する。JS で float RGB のバッファを作る。
  - 用意するシーン: ①屋内 + 窓の逆光(明るさ比 1:2000)②夕焼けのグラデーション ③カラーチャート ④3DCG風の球と床(擬似ライティング)⑤肌色のグラデーション帯
  - シーンは「シーンリニア値」で定義する。ここから各色空間へ変換して見せる。
- どうしても実写が要る箇所は **CC0 素材のみ**。出典を `assets/data/CREDITS.md` に記載する。
- ログ映像の見た目は、シーンリニア → 疑似 Log カーブで生成する。特定メーカーの正確な Log 曲線は名乗らず、「Log の一例」と書く。

### 5.5 色の実装精度

- 色空間の原色・白色点・行列は **公表値をコード内のコメント付きで持つ**。出典を書く。
- ACES の出力変換は **完全な実装をしない**。中学生向けに挙動を再現した **簡略トーンマップ** を使い、画面に「学習用の簡略版です。実際の ACES 出力変換とは細部が異なります」と明記する。これはサイト全体で守る誠実さのルール。
- 簡略トーンマップの仕様は `docs/INTERACTIVES.md` に定義する。

### 5.6 アクセシビリティ

- WCAG 2.1 AA を目標。本文のコントラスト比 4.5:1 以上。
- 色だけで情報を伝えない。色域比較・差分表示にはラベルとパターンを併用する。
- すべてのスライダーはキーボード操作可能 (`input[type=range]`)。値は数値でも表示し、直接入力もできる。
- 図版は SVG + `<title>`/`<desc>`。写真的な図には代替テキストで「何が見えるか」を書く。
- 難読漢字には `<ruby>` を付ける(中学生想定)。付ける対象は用語集で管理する。
- `prefers-reduced-motion` を尊重し、自動アニメーションを止める。
- 色覚シミュレーション(P型/D型)のトグルを色域比較の部品に付ける。教材としても機能させる。

### 5.7 対応環境

| 区分 | 対象 |
|---|---|
| ブラウザ | Chrome / Edge / Safari / Firefox の最新2バージョン |
| モバイル | iOS Safari 16+, Android Chrome 最新2 |
| 画面幅 | 320px 〜 |
| HDR 表示 | 対応判定して切り替え。非対応でも全内容が学べること |

HDR 表示の判定は `window.matchMedia('(dynamic-range: high)')` を用い、対応時のみ HDR 用の描画パスを使う。非対応時は擬似表現に明示的に切り替える。

### 5.8 プライバシー・外部通信

- アクセス解析、Cookie、外部への通信を **一切行わない**。
- 保存するのは進捗とテスト結果のみ、`localStorage` に閉じる。「保存内容を消す」ボタンを設置する。

## 6. 文章のルール

- 1文は40字程度まで。1段落は3文まで。
- 英語の用語は初出時に `OCIO(オープンカラーアイオー、色の変換ルールをまとめる仕組み)` の形で書く。
- 「〜と言われています」「〜のようです」を使わない。断定できないことは書かない。
- 専門家向けの正確な補足は `<details>` で畳んで「もっとくわしく」に入れる。本文の読みやすさを優先する。
- 数値は必ず単位を書く。nit, %, bit を省略しない。
