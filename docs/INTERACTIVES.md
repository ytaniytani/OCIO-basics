# インタラクティブ部品 詳細仕様

- 親文書: `docs/SPEC.md`
- 対象: I-01 〜 I-14
- 実装場所: `js/widgets/`

## 共通仕様

### 部品の外枠

すべての部品は次の構造を持つ。

```
┌─────────────────────────────┐
│ ▸ ねらい (1行)                 │  ← 何がわかるか
├─────────────────────────────┤
│  ビュー(画像・グラフ)            │
├─────────────────────────────┤
│  操作 (スライダー/トグル/ボタン)     │
├─────────────────────────────┤
│  よみとり (数値・ひとこと解説)       │  ← 状態に応じて変わる
└─────────────────────────────┘
        [ リセット ]  [ もっとくわしく ▾ ]
```

### 共通ルール

- **リセットボタンを必ず置く。** 壊しても戻せることを保証する。壊す体験を推奨するため。
- **数値は常に見える。** スライダーだけで数値を隠さない。数値の直接入力も許す。
- **状態に応じた1行コメント**を「よみとり」に出す。例:「いま光の量は4倍。でも画面の数値は2倍にもなっていません。」
- 比較は原則 **並べて表示**。切り替え式にする場合は A/B をワンタップで往復できること。
- 差分表示トグル(`|A - B| × 8` を可視化)を比較系の部品に付ける。
- 簡略実装の部品には「学習用の簡略版」バッジを右上に出す。

### 共通の内部表現

- 内部はすべて **シーンリニア float RGB**。表示直前にのみ表示用変換をかける。
- 色空間定義は `js/core/color.js` に集約。原色 (xy)、白色点、伝達関数(順・逆)、XYZ 行列を持つ。
- 変換の合成は `js/core/transforms.js` の `TransformChain` で行い、GLSL を生成する。

### 簡略トーンマップの定義(サイト共通)

ACES の実際の出力変換は実装しない。代わりに次の簡略版を使い、必ずその旨を表示する。

```
// 入力 x: シーンリニア (ACEScg想定), 出力: 0..1 のディスプレイ線形値
// peak: 目標ピーク輝度 (nit)。SDR=100, HDR=1000/4000
1. ホワイトバランス・行列変換で表示色空間へ
2. トーンカーブ: y = (x*(a*x+b)) / (x*(c*x+d)+e)   ← ACES風フィルミックの近似
   a=2.51, b=0.03, c=2.43, d=0.59, e=0.14
3. peak に応じてカーブのショルダー開始点と出力上限をスケール
4. 表示用伝達関数(sRGB / Rec.709 / PQ / HLG)でエンコード
```

このカーブは見た目の傾向を再現するためのものであり、実務用ではない。本文にも同じ注意を書く。

## I-01 光の量スライダー

- **章**: 1
- **ねらい**: 光の量という物理量と、画面に出る数値は別物だと知る。
- **見た目**: 中央に球体1つ。右に「光の量」スライダー(0〜16、対数目盛)。下に3本のメーター(光の量 / 保存される数値 / 8bit値)。
- **操作**: スライダー1本。倍率ボタン(×2, ÷2)も置く。
- **内部**: シーンリニア値 `L` を直接動かし、`sRGB_encode(tonemap(L))` で表示。
- **よみとり例**: 「光の量 2.0 → 保存される数値 0.73 → 8bitで 186」
- **合格基準**: ×2 ボタンを押しても、8bit の数値が2倍にならないことに気づける。

## I-02 二倍の光クイズ

- **章**: 3
- **ねらい**: 表示用の数値が曲げられていることを、当てて外して覚える。
- **流れ**:
  1. 「光の量が 1.0 のとき、画面の数値は 255 です。光を半分にしたら、数値はいくつ?」
  2. 選択肢: 128 / 186 / 220 / 64
  3. 回答後、正解 (≒186) とグラフを表示。「半分の光は、数値では 73%」
  4. 追加問題: 「数値が 128 のとき、光の量は?」→ 約 21%
- **合格基準**: 2問目で「半分ではない」と答えられる。
- **備考**: 間違えても responsive に否定しない。「多くの人がそう答えます」と書き、理由に進む。

## I-03 ガンマカーブ・エクスプローラ

- **章**: 3
- **ねらい**: 伝達関数を目で見る。色空間ごとに曲線が違うことを知る。
- **見た目**: 左にグラフ(横=光の量 0〜1、縦=保存値 0〜1)、右にグレースケール帯のプレビュー。
- **操作**:
  - 曲線の選択: リニア / sRGB / Rec.709 / ガンマ2.2 / ACEScct
  - グラフ上をドラッグすると読み取り線が動き、対応する2つの値を表示
  - 「横軸を対数にする」トグル(Log 系の形が見えるようになる)
- **よみとり**: 選択中の曲線の説明1行 + 中間グレー (0.18) がどこに来るか常時マーク。
- **もっとくわしく**: sRGB の分割式(閾値 0.0031308 の線形部分と 1/2.4 乗)を数式で提示。

## I-04 色度図と色域ビューア

- **章**: 2
- **ねらい**: 色空間ごとに「使える色の広さ」が違うと知る。
- **見た目**: CIE 1931 xy 色度図(馬蹄形)の上に三角形を重ねる。
- **操作**:
  - 色空間トグル(複数選択可): sRGB / Rec.709 / Display P3 / Rec.2020 / ACEScg (AP1) / ACES2065-1 (AP0)
  - 「白色点を表示」トグル
  - 「色覚シミュレーション」: なし / P型 / D型
  - 色度図をタップすると、その色が各色空間で表現できるかを ○/× で表示
- **注意表示**: 「この馬蹄形の中の色は、あなたの画面では正確に出せません。位置関係を見るための図です。」を必ず出す。
- **合格基準**: AP0 が馬蹄形をはみ出すこと(現実に存在しない色まで含む)に気づき、その理由の説明を読む。

## I-05 タグ違い事故シミュレータ

- **章**: 2
- **ねらい**: 数値が同じでもラベルが違えば別の色になる、を体感する。
- **見た目**: 同じ画像を2枚並べる。左「正しいラベル」、右「間違ったラベル」。
- **操作**:
  - 画像を選ぶ: カラーチャート / 夕焼け / 肌色帯
  - 本当の色空間: sRGB 固定
  - 解釈するラベル: sRGB / Rec.709 / Display P3 / Rec.2020 / リニア
  - 差分表示トグル
- **よみとり**: 「ラベルを Rec.2020 と間違えると、赤が濃くなりすぎます。数値は1ビットも変わっていません。」
- **拡張**: 「二重変換」モード。変換を2回かけてしまう事故も再現する。

## I-06 露出スライダー + クリップ体験

- **章**: 4
- **ねらい**: 8bit で焼いた画像とシーンリニアの画像で、後から救えるものが違うと知る。
- **見た目**: 逆光シーン(室内 + 窓)を2枚並べる。左「8bit JPEG にした画像」、右「シーンリニアのまま持っている画像」。
- **操作**:
  - 露出スライダー: -4 EV 〜 +4 EV
  - 「白飛びしているところを赤く表示」トグル(ゼブラ)
  - 「ヒストグラムを見る」トグル
- **挙動**: 露出を下げたとき、右は窓の外の景色が戻ってくる。左は真っ白のまま。
- **よみとり**: 「左の画像では、窓の外の情報は保存された時点で捨てられています。」
- **伏線**: 「右に残っているこの明るさが、第10章で HDR に使えます。」と表示する。

## I-07 リニア合成ラボ

- **章**: 5
- **ねらい**: 計算をどの空間でやるかで結果が変わることを、5つの操作で確かめる。
- **見た目**: 上に「リニアで計算」、下に「表示用の数値のまま計算」。同じ操作を並べる。
- **操作**:
  - 操作の選択: 加算(光を足す) / アルファ合成 / ぼかし / 縮小 / グロー
  - 操作の強さスライダー
  - 差分表示トグル、拡大鏡(境界を拡大)
- **各操作で見せたい違い**:
  | 操作 | 表示用空間でやると起きること |
  |---|---|
  | 加算 | 明るさが足りない。2つのライトを足しても暗い |
  | アルファ合成 | 境界に暗い縁や色にじみが出る |
  | ぼかし | 全体が暗くなる。明るい点の広がりが弱い |
  | 縮小 | 細かい模様が暗く沈む(モアレ部分が特に) |
  | グロー | 光のにじみが不自然。芯だけ明るい |
- **合格基準**: ぼかしの結果で「下の方が暗い」と気づける。
- **もっとくわしく**: 数値例。0.5 + 0.5 をリニアでやると 0.43 相当の光、sRGB のまま足すと 1.0 になる、という比較表。

## I-08 学園祭プロジェクト事故シミュレータ

- **章**: 6
- **ねらい**: 素材ごとに色空間が違うと作品が成立しないと知る。
- **見た目**: 4分割のタイムライン風レイアウト(スマホ動画 / Log映像 / 3DCG / 出典不明素材)+ 下に「つないだ結果」の横長プレビュー。
- **操作**:
  - **メインの OCIO トグル**(OFF / ON)。この部品の主役。
  - 素材ごとの入力変換を手動で選ぶモード(上級)
  - 「編集ソフトA / B で見る」切り替え(設定が共有されていない状況を再現)
- **OFF のとき**: CG が暗く沈み、Log が灰色、素材の明るさがバラバラ。ソフトA/Bで見え方も違う。
- **ON のとき**: 全部そろう。ソフトA/Bで同じ見え方になる。
- **よみとり**: OFF 時に「いま何が起きているか」を素材ごとに指摘する吹き出しを出す。
- **上級モード**: 入力変換をわざと間違えると、その素材だけ壊れる。原因が特定できる形にする。

## I-09 パイプライン組み立てパズル

- **章**: 6
- **ねらい**: 処理の順番に意味があると知る。
- **見た目**: 上部にブロック置き場、中央に4つのスロット、下に結果プレビュー。
- **ブロック**: `入力変換` / `作業空間で作業` / `ルック(味付け)` / `出力変換` + ダミー2枚(`ファイルに保存` `SNSに投稿`)
- **操作**: ドラッグ&ドロップ(タップ選択にも対応。モバイル必須)。
- **判定**: 正解の順に並ぶまで結果プレビューが壊れて見える。並び順ごとに固有の壊れ方を用意する(ランダムにしない)。
  - 出力変換を先頭に置く → 素材が二重に加工されて白っぽい
  - ルックを出力変換の後に置く → 味付けが強すぎる/破綻する(第9章の伏線)
- **ヒント**: 3回間違えると1つだけスロットが確定するヒントを出す。

## I-10 config.ocio ライブエディタ

- **章**: 7
- **ねらい**: 設定ファイルを自分で書き換え、絵が変わる体験をする。
- **見た目**: 2ペイン(モバイルはタブ切り替え)。左 = YAML エディタ、右 = プレビュー + display/view セレクタ。
- **エディタ機能**:
  - シンタックスハイライト(自前実装。外部ライブラリ不使用)
  - 行番号、エラー行のマーカー
  - 自動反映(入力停止 300ms 後)
  - スニペット挿入ボタン(色空間を追加 / look を追加)
  - リセット、課題ごとの初期状態に戻す
- **エラー表示**: 「10行目: `my_space` という色空間は定義されていません。`colorspaces` に追加するか、名前を確認してください。」の形で、日本語で原因と対処を書く。
- **課題**(順に解放):
  1. **色空間を足す** — `my_gamma22` を追加し、views に出して選べるようにする
  2. **ロールを壊す** — `scene_linear` を間違った色空間に向け、何が壊れるか観察してから直す
  3. **look を足す** — 少し青くする look を追加し、view に適用する
  4. **出力を替える** — 表示を Rec.709 から sRGB に切り替え、差分を見る
- **各課題の合格判定**: エンジンが実際に評価した結果と期待値を比較して自動判定する。文字列一致では判定しない。
- 詳細は `docs/OCIO-ENGINE.md`。

## I-11 ACES 全景マップ

- **章**: 8
- **ねらい**: ACES の流れを1枚で把握する。
- **見た目**: 横スクロールの帯。左から順に、素材 → 入力変換 → ACES作業空間 → ルック → 出力変換 → 各出力先。
- **操作**:
  - 各段をタップすると、その段での画のサムネイル + 1行説明 + 「なぜこの段が要るか」
  - 「素材を替える」: スマホ / Log / CG
  - 「出力先を替える」: 劇場 / SDRテレビ / HDRテレビ / スマホ
  - 作業空間の内訳(AP0 / AP1 / ACEScct)は、その段をタップすると展開する
- **注意**: 中間段の画は「そのまま画面に出すとこう見える」という説明を添える。作業空間の絵が眠く見えるのは異常ではないと明示する。
- **合格基準**: 出力先を替えても手前の段が変わらないことに気づける。これが第9章と第10章の土台。

## I-12 グレーディング位置ラボ

- **章**: 9
- **ねらい**: 味付けを入れる場所で結果が変わる。正しい場所が1つだと確かめる。
- **見た目**: 上に「どこに入れるか」の3択パイプライン図。下に結果を2列(SDR出力 / HDR出力)で表示。
- **操作**:
  - 挿入位置: 入力変換の前 / 作業空間の中(ACEScct) / 出力変換の後
  - グレード内容: 明るさ / コントラスト / 色み(青〜オレンジ) / 彩度 の4スライダー
  - 素材切り替え(スマホ / Log / CG)
  - 出力切り替え(SDR / HDR)
- **見せたい破綻**:
  - 「入力変換の前」: 素材を替えると効果が変わってしまう。素材ごとに調整し直しになる。
  - 「出力変換の後」: SDR で合わせた設定を HDR に持っていくと破綻する。白飛びが戻らない。彩度が暴れる。
  - 「作業空間の中」: 素材を替えても出力を替えても味付けが保たれる。
- **よみとり**: 位置を変えるたびに「この位置の問題点」または「この位置が良い理由」を1行で出す。
- **追加パネル**: LMT(作品全体)と ショットグレード(カット単位)の関係図。どちらも出力変換の前にあると示す。

## I-13 HDR 出力比較

- **章**: 10
- **ねらい**: 同じデータから複数の明るさの出力が作れると知る。
- **見た目**: 1つの ACES データ(逆光シーンまたは夜景)を、出力設定ごとに並べる。
- **操作**:
  - 出力: SDR 100nit / HDR 1000nit (PQ) / HDR 4000nit (PQ) / HLG
  - 「明るさヒートマップ」トグル: 各画素の目標輝度 (nit) を色分け表示 + 凡例
  - 「SDR で切り捨てられた部分」ハイライト
  - 明るさメーター: マウス/指を置いた点の nit を表示
- **HDR 対応環境**: `(dynamic-range: high)` が真なら本物の HDR で描画する。画面上に「あなたの画面は HDR 表示に対応しています」と表示。
- **非対応環境**: 擬似表現に切り替え、「あなたの画面は SDR です。HDR の見え方をシミュレーションしています」と常時表示する。ヒートマップとメーターは非対応でも正しく機能するので、学習は成立する。
- **締め**: 「1マスター多出力」図。ACES マスター1本から4つの出力が枝分かれするアニメーション。第4章のスクリーンショットを並べ、「あのとき残しておいた明るさが、ここで使われました」と接続する。

## I-14 チェックテスト

- **章**: 11
- **構成**: 選択式8問 + 画像判定2問。
- **画像判定問題の例**:
  - 「この画像は何が起きている?」→ 選択肢: 入力変換の指定ミス / 二重変換 / リニアのまま表示 / 正常
  - 「このパイプラインの間違いはどこ?」→ 図の中の該当ブロックをタップ
- **採点**: 即時。間違えた問題には「第○章のここを見よう」のリンクを出す。
- **保存**: `localStorage` に結果を保存。共有・投稿機能は作らない。
- **必ず含める設問**:
  - OCIO が無いと何が困るか
  - 中間グレーの数値と光の量の関係
  - 計算をリニアでやる理由
  - グレーディングを入れる位置
  - ACES で HDR と SDR の両方が出せる理由

## 実装の優先順位

| 優先 | 部品 | 理由 |
|---|---|---|
| 1 | I-05, I-07, I-08 | 「無いと困る」を成立させる中核。これだけでもサイトの価値が出る |
| 2 | I-01, I-02, I-03, I-06 | 基礎の土台。他の部品の前提になる |
| 3 | I-10 | 体験の目玉。エンジン実装が要るので時間がかかる |
| 4 | I-11, I-12, I-13 | ACES / グレーディング / HDR の本題 |
| 5 | I-04, I-09, I-14 | 補助と仕上げ |
