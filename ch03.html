第3章

明るさの数字は正直じゃない

色空間の3つめの約束、伝達関数の話です。ここが分かると、第5章の「なぜ計算が壊れるのか」に一気につながります。

50%グレーは、本当に半分?

画像ソフトで「50%のグレー」を作ります。数値でいうと 8bit の 128 くらいです。

8bit というのは、明るさを真っ黒 0 から真っ白 255 までの 256段階で表すやりかたのことです。だから 128 はちょうどまん中の段階になります。同じ明るさを 0.0〜1.0 で書くこともあり、その場合は 0.5 です。

このグレーは、白の半分の明るさでしょうか。まずは自分で予想してから、下の問題に答えてみてください。

ここは動かして見る部分です

JavaScript を有効にすると、2問のクイズで確かめられます。答えを先に書いておくと、光を半分にしたときの 8bit の値は 128 ではなく 188 です。逆に 8bit の 128 は、光の量にすると 21.6% しかありません。

答えは 21.6% でした。半分どころか、5分の1くらいしかありません。

わざと曲げてあります

光の量と数値が正直に対応していたら、光を半分にすれば数値も半分になるはずです。まっすぐな比例の関係、ということです。でもさっきのクイズどおり、光を半分にしても数値は 188 までしか下がりませんでした。

光の量と数値の関係は、まっすぐな比例ではなく、途中で折れ曲がっています。暗い光にはたくさんの数値を、明るい光には少しの数値を割りあてる、という曲がりかたです。このサイトでは、この関係を「曲げる」と呼びます。どんな形に曲がっているかは、あとの「さわる」でグラフに描いて見せます。

これはバグではありません。わざとそうしてあります。理由は2つです。

理由1: 人の目は暗いところに敏感だから

人の目は、暗いところのわずかなちがいはよく見分けられますが、明るいところのちがいにはにぶくなっています。だから数値の段階は、暗い側に多く割りあてたほうが得です。

理由2: 8bit は256段階しかないから

ふつうの画像は1つの色あたり256段階しか持てません。もし光の量をそのまま素直に記録すると、暗い部分に使える段階が足りなくなり、空のグラデーションなどに縞(しま)が出ます。

そこで、暗い側をひきのばして段階を多く配り、明るい側は詰める、という曲げかたをします。この曲げかたのルールが 伝達関数 です。ガンマ という言葉も、ほぼ同じ意味で使われます。

曲がりかたを目で見る

横が光の量、縦が保存される数値です。線の上を指でなぞると、対応する2つの値が読めます。曲げかたを切りかえて、形のちがいを見てください。

グラフには 「中間グレー 0.18」 という印が出ます。先にこれが何なのかを説明しておきます。

「中間グレー」とは何のことか

「中間グレー」は、このサイトだけの言葉ではありません。写真・映像・CG のどの現場でも使う、ふつうの言葉です。英語では middle grey、または 18% グレーと言います。

指しているのは、当たった光のうち 18% を反射する灰色のことです。カメラ用品の店には、そのとおりに作った「グレーカード」という板が売っています。撮影のとき画面に入れて、明るさの基準にするための道具です。

だから 0.18 は光の量のほうの数字で、0〜255 のうちの 0.18 ではありません。光の量は「真っ暗が 0.0、白い紙が 1.0」として書きます。その 0.18、ということです。

「中間グレー」と聞いて、こう思いませんでしたか

思ったこと答え
人の目に、白と黒のちょうどまん中に見える灰色のこと? ほぼ合っています。18% の光を sRGB で保存すると数値 0.461、8bit で 118。0〜255 のまん中あたりです。人がまん中と感じる灰色は、光の量では半分ではなく5分の1くらいしかない ── これがこの章の話そのものです。
カメラが露出を合わせるときの基準? 合っています。グレーカードを写して明るさの基準にするのは、いまでもふつうのやりかたです。CG や映像の計算でも、この 0.18 を基準の明るさとして使います。
白と黒のチェック模様を遠くから見たときの色? これはちがいます。白と黒が半分ずつなら、返ってくる光は約 50% で、18% ではありません。光の量 50% は 8bit で 188 になり、中間グレーよりずっと明るい灰色に見えます。

ここは動かして見る部分です

JavaScript を有効にすると、sRGB、Rec.709、ガンマ2.2、ACEScct、Log などの曲線を切りかえて比べられます。点線がリニア(曲げない場合)です。sRGB の線はそれより上にふくらんでいて、暗い光にも大きめの数値を割りあてていることが分かります。

見どころが3つあります。

  • 点線(リニア)より上にふくらんでいる。 暗い光にも大きめの数値を割りあてている、という意味です。
  • 中間グレー 0.18 の印。 曲げかたを切りかえても、横(光の量)は 0.18 のまま動きません。動くのは縦(保存される数値)のほうだけです。
  • ACEScct と Log は、1.0 を超える光も収まる。 Log(ログ)は、とても広い明るさを 0〜1 の中に詰めこむ記録のしかたです。ACEScct(エーシーイーエス・シーシーティー)は、その考えかたを色の調整用に整えたものです。どちらも第8章と第9章でまた出てきます。「横軸を対数にする」を押すと、Log の線がまっすぐになります。

計算するときは、曲げをほどく

曲げてあること自体は問題ありません。問題は、曲がったままの数値で計算してしまうことです。

足し算も平均も、光の量に対してやらないと正しい答えになりません。だから計算の前に曲げをほどいて光の量にもどし、計算が終わってから、見るためにまた曲げます。

この「ほどく」「曲げる」を、素材ごとに正しくやってくれるのが OCIO です。曲がったまま計算すると具体的に何が起きるのかは、第5章で実際に見ます。

この章のまとめ

  • 画面用の数値は、わざと曲げてある。暗い側に段階を多く割りあてるため。
  • 8bit(0〜255の256段階)の 128 は、光の量では 21.6% しかない。
  • 光の量を半分にしても、8bit の値は 188 までしか下がらない。
  • 計算するときは、いったん曲げをほどいて光の量にもどす。
まえ数字だけでは色は決まらない つぎ見える範囲がちがう
